# Открытие и чтение файла tasks.data

Этот документ описывает процесс открытия файла `tasks.data` и чтения шаблонов задач (`ATaskTempl`), основываясь на реализации в проекте и анализе исходного кода.

## 1. Структура файла tasks.data

Файл `tasks.data` представляет собой бинарный пакет, содержащий все шаблоны задач игры.

### Заголовок (Header)
В начале файла находится заголовок `TASK_PACK_HEADER` (12 байт):

| Тип | Размер | Описание |
|---|---|---|
| `int32` | 4 байта | **Magic Number**: Константа проверка целостности (`-1819966623` / `0x938833E1`). |
| `int32` | 4 байта | **Version**: Версия файла задач (например, `105`, `118` и т.д.). |
| `int32` | 4 байта | **Item Count**: Количество задач в файле. |

### Таблица смещений (Offset Table)
Сразу за заголовком следует массив смещений:
*   Массив чисел `int32` размером `Item Count`.
*   Каждое число указывает абсолютное смещение (offset) в байтах от начала файла до начала данных конкретной задачи.

### Данные задач
Далее следуют данные самих задач, расположенные по указанным смещениям. Порядок задач в файле данных может быть произвольным, но таблица смещений позволяет получить доступ к любой задаче по индексу.

### Индексация подзадач (Memory Mapping)
В Node.js реализации, помимо линейного списка смещений, строится **рекурсивная карта индексов** (`taskMap`). 
1. Сервер проходит по всем квестам верхнего уровня.
2. Если квест имеет подзадачи, он рекурсивно обходит их.
3. ID каждой подзадачи (даже глубоко вложенной) сохраняется в `taskMap` со ссылкой на индекс **файла-родителя**.
   
Это позволяет мгновенно находить любой подквест по его ID, даже если физически он находится внутри большого блоба данных родительского квеста.

## 2. Алгоритм чтения (Node.js)

В Node.js проекте чтение реализовано в классе `TaskFile` (`NodeTaskEdit/lib/TaskFile.js`).

### Шаг 1: Открытие и чтение заголовка
При вызове `load(filePath)`:
1.  Файл считывается полностью в буфер.
2.  Считываются первые три числа `int32`: `magic`, `version`, `count`.
3.  Производится проверка `magic` (хотя в текущем JS коде жесткой валидации может не быть, C++ код проверяет это строго).

### Шаг 2: Чтение таблицы смещений
Циклом от 0 до `count` считываются смещения и сохраняются в массив `offsets`. Это позволяет "знать", где находится каждая задача, не считывая их данные сразу (ленивая загрузка или индексация).

### Шаг 3: Чтение шаблона задачи
Для чтения конкретной задачи используется метод `loadQuest(index)`:
1.  Берется смещение из `offsets[index]`.
2.  Курсор потока (`TaskStream`) перемещается на это смещение (`seek`).
3.  Вызывается фабрика `TaskTemplFactory.create(version, stream)`.
4.  Фабрика создает экземпляр парсера (например, `ATaskTemplFixedDataV105` или `ATaskTemplFixedDataV118`) в зависимости от версии файла.
5.  Парсер считывает данные задачи согласно структуре `ATaskTempl`.

## 3. Алгоритм чтения (С++ / Reference)

Алгоритм, используемый игровым сервером (см. `ATaskTemplMan::LoadTasksFromPack` в `libtask.so`), аналогичен:

1.  `fopen` открывает файл.
2.  `fread` читает заголовок. Проверяется Magic и Version.
3.  Выделяется память под массив смещений (`new []`).
4.  Циклом считываются смещения (`fread` массива).
5.  **Основной цикл загрузки**:
    *   Переход по смещению: `fseek(fp, pOffs[i], 0)`.
    *   Создание нового объекта задачи: `new ATaskTempl`.
    *   Вызов метода загрузки: `ATaskTempl::LoadFromBinFile(ATaskTempl*, FILE*)`.
        *   Внутри вызывается `LoadBinary` -> `ATaskTemplFixedData::LoadFixedDataFromBinFile`.
    *   Если загрузка успешна, задача добавляется в менеджер: `ATaskTemplMan::AddOneTaskTempl`.

## 4. Чтение шаблонов (ATaskTempl)

Шаблон задачи (`ATaskTempl`) состоит из множества полей. Основные этапы чтения одной задачи:

1.  **Fixed Data**: Читаются фиксированные поля (ID, имя, требования, флаги и т.д.). В C++ это делает `ATaskTemplFixedData::LoadFixedDataFromBinFile`.
    *   Читаются 13 основных флагов булевого типа (HasSign, HasItems, etc — *в старых версиях структура может отличаться*).
    *   Читаются параметры: ID, Type, TimeLimit, Mode, и т.д.
    *   Читаются списки требований: `PreQuest`, `Lev`, `Items`, `Reputation`, и т.д.
2.  **Awards**: Читаются данные о наградах (`AWARD_DATA`). В зависимости от версии и флагов могут быть разные ветки наград (Failure, Success, RatioScale).
3.  **Sub-tasks / Conversations**: Читаются диалоги и подзадачи.

Особенностью формата является строгая зависимость от версии (`version`). При добавлении новых полей в новых версиях игры (1.4.x, 1.5.x+), структура смещается, поэтому для каждой версии нужен свой парсер или условия `if (version >= X)`.
